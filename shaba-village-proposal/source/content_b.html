Multi-tenancy and SaaS design

Every business on the platform is a tenant. Tenants share the software and infrastructure, never each other's data or money.

Tenant model

LevelOwned byDescription
Tenantauth-apiThe organisation: legal name, KRA PIN, branding, contacts, staff, roles and plan. The same tenant record is used by treasury, ERP, notifications and subscriptions, so a property tenant gets accounting, payroll and messaging with no second sign-up.
Portfolioproperty-apiA group of properties. An estate operator has one; a property manager has one per landlord client, carrying the management mandate, fee rules and remittance account.
Propertyproperty-api, registered as a branch in auth-apiAn estate, building, plot or complex. Each property is also an auth-api branch, so the platform's existing branch-scoped roles assign staff to specific properties.
Block, unitproperty-apiPhysical structure and the lettable or saleable spaces, each with use (residential, office, retail, industrial, parking, land), size and status.
Partiesproperty-api, with auth-api user IDsOwners, buyers, landlords, lessees and occupants linked to units by dated relationships.

Isolation

ControlImplementation
Data isolationShared database with tenant_id on every row and PostgreSQL row-level security, so a missing filter in code still cannot read another tenant's rows. Separate schema or separate database available for large or regulated tenants, the platform's standard isolation tiers.
Request scopingTenant taken from the signed token, never from a request parameter alone; branch scope applied for property-level roles.
MoneyEach tenant's own paybills, bank accounts and ledgers in treasury. A payment to one tenant's paybill can only ever be matched within that tenant.
FilesObject storage paths prefixed by tenant; signed, short-lived links checked against tenant and role.
MessagingTenant sender IDs and WhatsApp numbers; messages carry the tenant's name and contacts.
Fair useRate limits and job queues per tenant, so one tenant's billing run or import never slows another.
Cross-tenant identityA person has one sign-in; each tenant sees only its own relationship. Marketplace profiles are separate from tenant records and shared with a lister only when the seeker enquires.
ExitPer-tenant export and deletion without touching other tenants.

How configuration changes the product

A feature is available only where three conditions meet: the tenant's plan includes it, the tenant has switched the module on, and the property's use case includes it. Releases not yet live are hidden for everyone. The result is applied in every layer:

LayerBehaviour
Navigation and dashboardsMenus, tiles, quick actions and dashboard widgets are built from the enabled modules; a property manager with no gate module never sees passes or patrols
Forms and recordsFields, tabs and steps of disabled modules are not shown; a unit form shows sale fields only when sales is on, and lease fields only when leasing is on
Onboarding and set-upThe set-up wizard asks only for what the enabled modules need, for example meters only when utilities is on
Customer portalsOwners, lessees and landlords see only the screens that apply to their relationship and the property's modules
Roles and permissionsPermissions of disabled modules cannot be granted; role templates follow the use case
APIRoutes of disabled modules return a clear "module not enabled" response; checks run on the server, so hiding a button is never the only control
Background jobs and eventsBilling runs, reminders, SLA timers and event consumers run only for tenants and properties with the module on, so nothing is billed, sent or written for unused features
Notifications, reports and exportsMessage templates, reports and export columns follow the enabled modules
Switching offTurning a module off hides it and stops its jobs, but keeps its data read-only and exportable; turning it back on resumes from the same data

Module and use case settings are cached with the tenant profile and invalidated on change, so the check adds no noticeable latency.

Configuration over customisation

Everything that differs between businesses is configuration, not code. Shaba Village is configured, not customised; the next estate, property manager or landlord starts from the same product and the same seeded defaults, and changes only what is different about it. Settings are layered, and the most specific level wins:

Plans and gating

Each tenant's plan is held in subscriptions-api. Feature and limit checks (units under management, staff users, modules such as sales, leasing or marketplace publishing) run on every request and in event consumers, following the platform's subscription gating standard. A lapsed subscription keeps data readable but stops new records, never deleting anything.

Tenant onboarding

  1. Organisation created in auth-api (assisted in Release 1, self-service sign-up with trial from Release 2), with plan assigned.
  2. Tenant type chosen (estate operator, property manager, landlord), which loads the matching defaults: charge types, document templates, roles.
  3. Paybills and bank accounts connected in treasury; ledgers and cost centres created.
  4. Properties, units, parties and balances imported from templates, with a dry run.
  5. Staff invited and assigned to properties; providers loaded.
  6. Go-live checklist completed: live KES 1 payment tests, one parallel billing run, legal templates approved.

Architecture principles

  • Tenant first. Tenant ID on every table, row, event, cache key, file path and job; isolation tested on every release.
  • Single data owner. property-api stores treasury account, invoice, plan and vendor IDs, ERP employee IDs and auth user IDs, and reads balances from treasury.
  • Single payment path. Only treasury-api talks to M-Pesa and banks.
  • Event driven. Payment, invoice and payout events reach property-api through the transactional outbox and NATS; consumers are idempotent by event ID.
  • Replica safe. Billing runs, reminders, SLA timers, remittances and purges run once per period across replicas using shared leases.
  • Public and private separated. The marketplace reads a published projection of listings; it has no route to tenant operational data.
  • Standard stack. Go with Ent and Atlas migrations, Next.js, Helm and ArgoCD.
