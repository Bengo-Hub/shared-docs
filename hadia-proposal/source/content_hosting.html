Hosting, backup and disaster recovery

This section states where Hadia's data is held, how it is backed up and how service is restored after a failure.

Hosting location

ComponentProvider and locationContent
Application and database serversContabo Cloud VPS, European Union region (Germany). Dedicated virtual server: 12 vCPU, 47 GB RAM, 484 GB NVMe storage, running Kubernetes (k3s)hadia-ui, hadia-api, treasury, authentication, notifications; PostgreSQL databases
Offsite backupsCloudflare R2 object storage, separate provider and infrastructure; encrypted at restNightly encrypted database backups
Edge networkCloudflare (TLS termination, CDN, web application firewall)Traffic in transit and cached public assets; no database content
EmailCodevertex mail server (mx1.codevertexafrica.com) on the same platformOutbound email; no third-party email processor
FundsPayHero, KenyaGift funds and payment records. Funds never reside on Codevertex infrastructure.

Hosting outside Kenya is a cross-border transfer under sections 48 to 50 of the Data Protection Act. The transfer is documented in the DPIA with its safeguards: provider security certification, encryption in transit and at rest for backups, access restriction and a data processing agreement. Hosting in a Kenyan data centre is available on request and would be quoted as a change to the hosting cost.

Recovery objectives

ObjectiveTargetMeaning for Hadia
Recovery point objective (RPO)24 hoursIn the worst case, total loss of the server, changes made since the last nightly backup are restored from other sources. Contributions and payouts in that window are recovered from PayHero's transaction records and re-reconciled, so no payment record is lost. Registry edits, item changes and reservations made in that window may need to be re-entered.
Recovery time objective (RTO)4 hoursService is restored on a replacement server within 4 hours of a declared disaster.
Optional enhanced RPO15 minutesContinuous database log archiving to offsite storage, quoted on request.

Restore testing

A restore drill is performed quarterly: the latest offsite backup is restored into an isolated environment, record counts and ledger balances are verified against production, and a short report is shared with Hadia. The first drill takes place before launch, in week 11.

Platform outage response

ScenarioImpactResponse
Service or pod failureSeconds to minutesAutomatic restart; two replicas per service; health checks every 2 minutes with alerting
Server failure or provider outagePlatform unavailableAutomated rebuild on a replacement server from version-controlled configuration and backed-up encryption keys, followed by restore of the latest backup and reconciliation with PayHero.
During any outageGuests cannot contribute; payouts pauseFunds remain safe in Hadia's PayHero wallet. Pending payouts resume automatically on recovery. Hadia is notified within 30 minutes of a confirmed incident and updated every 2 hours.

Capacity scales by adding nodes to the cluster under a documented procedure, without service interruption. Additional capacity is planned with Hadia as monthly contributions grow.
