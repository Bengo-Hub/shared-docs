Legal, regulatory and compliance

Please read this first. This chapter maps the laws we know apply to an online gifting and payments business in Kenya and shows how the design meets them. It is a technical compliance plan, not legal advice. Before launch, Hadia's own Kenyan advocate should review the legal pack and confirm the points marked "confirm". Building these protections in from the first sprint is far cheaper than retrofitting them after a complaint.

Delivery methodology

We deliver in short Agile sprints with a working demo every week, so Hadia sees real progress early and can change direction while it is cheap to do so.

PracticeHow it works on this project
SprintsA one-week Sprint 0, four two-week sprints, a one-week Sprint 5, then a test week and a launch week.
Weekly demoEvery Friday, a 30 minute call with Tracey on the staging site. Decisions recorded in the shared backlog.
BacklogUser stories traced to the FR and NFR IDs in this document, each with acceptance criteria written before work starts.
Definition of doneCode reviewed, automated tests passing, accessibility checks passing, documented, deployed to staging, accepted by the product owner.
EnvironmentsDevelopment, staging and production on the Codevertex cluster. Staging uses provider sandboxes where they exist and live KSh 1 tests where they do not.
QualityUnit and database tests for each service, end-to-end browser tests for the guest and owner journeys, contract tests on the treasury and auth calls, load test before launch.
ReleaseGitHub Actions builds and tests every change; ArgoCD deploys from Git, so every release is traceable and reversible.
ReportingA short written status each Friday: done, next, risks, decisions needed.
Change controlNew ideas go to the backlog. Within the fixed price, Hadia may swap a requirement for one of similar size. Larger changes are estimated in time and cost first, and only proceed with written approval.

Appendix A: ecosystem audit findings

Before writing this proposal we audited the Codevertex services Hadia will rely on, so the plan reuses what exists, avoids duplicate logic, and does not inherit problems that would appear as Hadia grows.

Already fixed during the audit

ServiceFindingChange
treasury-api escrowThe 5-minute payout job read every auto-release pot into memory and checked each wallet balance with its own query.The job now reads only pots that can pay out now (rule can fire, money in the wallet), in pages of 200, with balances loaded in one query per page.
treasury-api escrowEscrow totals for the dashboard and the hourly reconciliation loaded every pot and wallet.Totals are summed in the database, grouped by tenant; only pots with a payout in flight are read.
treasury-api escrowA refund result scanned all of a tenant's cancelled pots to find its own.The pot is found directly from the code in the refund reference.
treasury-api escrowPayout results looked up the pot by its in-flight reference without an index.New partial index on the in-flight reference, with a versioned migration.
shared-ui-libThe legal footer always showed Codevertex's business details.LegalLinks accepts the tenant's own business details (version 0.1.102), which Hadia's footer uses.

Built as part of this project

  • auth-api: passwordless phone OTP sign-in for consumers (today OTP is available only to signed-in users).
  • treasury-api: scheduled commission sweep with a locked, verified destination; per-pot minimum and maximum contribution.
  • notifications-api: Hadia message templates and sender ID.
  • hadia-api: consumer for treasury's escrow events.

Noted for the platform team

  • The PayHero guide says escrow can run on a tenant's own PayHero account, while the escrow readiness check requires a Team account. Hadia's plan uses a Team, and the guide will be aligned.
  • Creating PayHero Teams by API needs PayHero's enterprise plan on the platform organisation; until then a Team created by PayHero is linked to the tenant. This is on Hadia's onboarding track.
