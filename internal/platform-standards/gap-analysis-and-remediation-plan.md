# Best-Practices Gap Analysis & Remediation Plan

> **INTERNAL ONLY — do not publish.** This file lives under `shared-docs/internal/` specifically because it is not built into the public docs site (see `mkdocs.yml`'s `docs_dir`). It's the fleet-wide, centralized record of known infrastructure/architecture gaps — effectively a map of the platform's current weak points — which is exactly the kind of thing that shouldn't be handed to the public alongside the developer-facing guide content. The published [Platform Engineering Standards](../../docs/platform-standards/index.md) pages describe how each piece of infrastructure works and are safe to publish; they deliberately do NOT restate the gap analysis below. Cross-referenced from the project's own memory system — see `d:\Projects\Codevertex\.claude\memory\deferred-and-open-items.md`.

Compiled 2026-08 from a live prod cluster inspection (`ssh mss-prod` / `kubectl`) plus a targeted scan of `shared/` and `devops-k8s/`, checked against a general best-practices reference spanning codebase, deployment, scalability, security, and performance. This page is the single compiled list — the individual [Platform Engineering Standards](../../docs/platform-standards/index.md) pages used to link back here for the specific gaps they called out; that cross-linking was removed when the public pages were rewritten to be gap-free, so this file is now the only place this analysis lives. **Nothing on the "confirmed gaps" list below has been implemented as part of this audit** — this is a gap analysis and proposed task list for sign-off, not a changelog. Prod-infrastructure changes carry real blast radius and should be reviewed and approved individually before work starts.

## Confirmed gaps — prioritized remediation task list (proposed, needs sign-off per item)

### Must-have

1. ~~**No observability stack.** Zero Prometheus/Grafana/Loki/tracing-backend pods anywhere in the cluster... Proposed: deploy kube-prometheus-stack + Loki.~~ **NOT A GAP — corrected 2026-08-06, re-confirmed and fully closed out 2026-08-16.** This framing was stale against a deliberate decision: `devops-k8s` commits `aa18b5ca`/`402faacc` (2026-07-13) decommissioned the self-hosted kube-prometheus-stack on purpose, its own message stating "Replaced by lightweight admin-panel scripts on auth-service reading kubectl top / metrics-server directly." A session that treated this line item at face value nearly re-deployed the full stack in 2026-08-06 (caught before anything went live). Separately, an out-of-band `kubectl apply` of a full `kube-prometheus-stack` release (ArgoCD Application `prometheus`, bypassing this repo's GitOps path entirely) was found actually running live in `infra` on 2026-08-16 during a production incident post-mortem — origin unknown, never landed in this repo or its history. The user explicitly revisited the decision that day and confirmed: tear it down for good. Fully removed 2026-08-16: the ArgoCD Application, all Helm-release-owned workloads/services/ingress/secrets/configmaps/ServiceMonitors (64 resources), the `Prometheus`/`Alertmanager` CRs and their StatefulSets, all 3 PVCs (40Gi), all 10 `monitoring.coreos.com` CRDs, plus long-orphaned leftovers from the *original* pre-decommission release (`monitoring-grafana` secret/configmaps, `grafana-tls`, `prometheus-kube-prometheus-admission` — all 243-257 days old, never cleaned up until now) and this repo's own dead `manifests/monitoring/`, `docs/monitoring.md`, `scripts/monitoring/`. The gap this closed — no push-based alerting — is now handled by `fleet-health-watcher` (a lightweight CronJob, Slack + email), not a re-deployed TSDB stack. **Do not propose re-deploying Prometheus/Grafana/Loki again without the user explicitly revisiting this decision first** — that's now happened twice; a third occurrence should be treated as a strong signal to actually ask the user directly rather than infer it from a stale doc line again.
2. **LANDED 2026-08-07 (controller + pilot); re-verified still current 2026-08-21, migration now proceeding.** Sealed Secrets controller (bitnami chart v2.19.1, not External Secrets Operator — no external KMS/Vault exists in this stack, so ESO would add an operator layer for no benefit over Sealed Secrets' simpler in-cluster-keypair model) is live in `kube-system`, verified via `kubeseal --fetch-cert`. `apps/sealed-secrets-manifests/app.yaml` scaffolds directory-sync of future per-service `SealedSecret` files so migrating a new service is just "add a file" — no new Application needed per service. Pilot migration (`library-api-secrets`) completed and fully verified: the `SealedSecret` now owns the resulting Secret, all 13 original keys intact, consuming pods undisturbed throughout. Two operational gotchas hit and resolved — the controller won't take over a pre-existing plain Secret, and won't re-reconcile on that Secret's deletion alone (needs a controller pod restart to force a fresh full reconcile) — documented in `.claude/memory/reference_sealed_secrets_migration_gotchas.md` for every future per-service migration. No dashboard/UI for Sealed Secrets — that's by design (the decrypting key never leaves the cluster); a future thin admin-panel wrapper was discussed and deferred, not built. **Re-verified live 2026-08-21: still only `library-api` migrated** — `pos-api`/`inventory-api`/`treasury-api`/`auth-api`/`subscriptions-api` all still provisioned as plain Secrets via `create-service-secrets.sh`. Migration of the 5 critical services is now in progress, ascending blast radius: `pos-api → inventory-api → subscriptions-api → treasury-api → auth-api` (auth/treasury still deliberately last, per the original plan, despite auth being the service most recently named for audit attention — the ordering is about blast radius of a migration mistake, not about which service matters most).
3. **LANDED 2026-08-06; re-verified 2026-08-21, one sub-gap found and closed same day.** All three pieces live and verified on prod: PgBouncer `replicas: 1→2` + a `PodDisruptionBudget`; a new, purely-additive Postgres streaming-replication standby (`pg_basebackup`-primed, confirmed via `pg_stat_replication` showing `state=streaming` with single-digit-millisecond lag, write-rejection confirmed, zero primary downtime during setup); a new, purely-additive Redis replica (confirmed via an actual write-on-master/read-from-replica propagation test, not just a link-up check). This is single-node accepted-risk HA — protects against a primary pod crash/OOM/bad-migration, not node/disk failure, since both pods share the same physical disk. No automatic failover for either database; manual-promotion runbook documented in `shared-docs/internal/operations/database-maintenance.md`. The "should this be monitored via Prometheus" question flagged in the prior note was resolved by not needing it — `pg_stat_replication`/Redis `INFO replication` plus the existing lightweight kubectl-based approach were sufficient to verify and will be sufficient to operate this going forward. **Found and fixed same day (2026-08-21): the `postgresql` StatefulSet itself had no PodDisruptionBudget** (pgbouncer and redis-master each had one; the primary database didn't) — added (`devops-k8s a3d7f833`, applied via `kubectl` directly after `provision.yml` got raced/cancelled — see the release-bot-race note below), verified live (`kubectl get pdb postgresql -n infra` shows `minAvailable=1`).
4. ~~**Rate-limiting logic duplicated per-service instead of centralized.**~~ **DONE 2026-08-06:** extracted to `github.com/Bengo-Hub/shared-ratelimit` (`Limiter` for treasury-api's sliding-window abuse throttling, `Quota` for notifications-api's daily plan-quota metering); both services migrated. See [Rate Limiting](../../docs/platform-standards/rate-limiting.md) (updated).
8. ~~**New 2026-08-21 — no NetworkPolicy or Pod Security Standards anywhere in the cluster.**~~ **NetworkPolicy CLOSED for the 6 highest-risk services same day (2026-08-21).** `kubectl get networkpolicy -A` had returned only ArgoCD/Calico-apiserver/ollama-shared entries — zero pod-to-pod isolation existed for `pos`/`inventory`/`treasury`/`auth`/`subscriptions` (or any other app namespace); any pod that could reach the cluster network could reach any other service's pods, PgBouncer, and Redis directly. Fixed via ingress-only `NetworkPolicy` manifests (new `manifests/network-policies/` directory-sync Application, mirroring `sealed-secrets-manifests`' pattern) — deliberately Ingress-only, NOT using the shared `charts/app` chart's own bundled `networkpolicy.yaml` template, whose default Egress allow-list (only `infra` namespace + external :443) would have silently broken cross-namespace S2S calls (confirmed against library-api's real NATS/treasury/notifications/subscriptions dependencies — a real footgun in that shared template worth fixing before anyone else flips `networkPolicy.enabled` on it). Piloted on `library-api` (`devops-k8s d79a20d9`) then extended to all 5 critical services (`devops-k8s f62bc387`/`86139a7c`/`a1a4b397`/`aa126c77`/`3c59c77e`). **Each namespace's consumer list was derived two ways, and the second check found a real miss the first alone would have shipped as a live-outage risk**: (1) grepping every `apps/*/values.yaml` for explicit internal-DNS overrides, and (2) grepping every service's Go `config.go` for a compiled-in default already pointing at internal DNS with *no* values.yaml override — treasury-api's own `SUBSCRIPTION_BASE_URL` defaults straight to subscription-api's internal DNS this way, invisible to a values.yaml-only grep. The same sweep also surfaced a separate, pre-existing, unrelated bug (documented, not fixed, not allow-listed): logistics-api's treasury client defaults to port 4005, but treasury-api's Service only exposes 4000 — already broken before this policy existed. Every one of the 6 policies was live-verified, not just deployed: 0 new pod restarts, the service's public hostname still responds, every real consumer namespace confirmed reachable via a live in-cluster request, and at least one non-allow-listed namespace confirmed genuinely blocked (`HTTP 000`) per service. **Pod Security Standards labels remain unaddressed** — out of this pass's scope, a separate future item.
9. **New 2026-08-21 — VPA live-in-cluster but absent from GitOps; KEDA installed but unused. GitOps-capture LANDED same day for VPA.** `kubectl get vpa -A` showed a VPA object (mode `Off`) for all 5 critical services, but none of their `values.yaml` defined a `verticalPodAutoscaling` block — these were applied out-of-band and were pure cluster drift, not GitOps-managed. Fixed: added the matching block (mode `Off`, matching live state exactly — a mode change is a separate, later decision) to all 5 `values.yaml` (`devops-k8s a3d7f833`), verified zero behavior change (same spec, same object age, no recreation). Separately, the KEDA operator is running (3 pods, `infra`) but zero `ScaledObject`s exist anywhere — the earlier "HPA + VPA + KEDA, fleet-wide" framing in this doc's own "confirmed working well" table overstated actual KEDA usage; KEDA is an installed, unused capability, not an active autoscaling mechanism, and is left as-is (a capability to reach for on a future queue-depth-sensitive workload, not something that needs a `ScaledObject` today just to prove it works).

**Recurring operational footgun found this pass (not itself a gap item, but worth recording here since it affected several of the fixes above):** `devops-k8s`'s `provision.yml` — the workflow that applies new/changed ArgoCD `Application` CRs (as opposed to plain `values.yaml` content, which ArgoCD picks up on its own git-polling cycle) — gets raced and cancelled by the very next push almost every time (matches [[reference_devops_k8s_release_bot_ci_race]]). Every `app.yaml`-level change in this pass (the `postgresql` Application's `directory.include` edit, the new `network-policies` Application) needed a direct `kubectl apply -f apps/<x>/app.yaml` fallback after confirming via `gh run list` that the workflow run was cancelled. Worth fixing at the workflow level eventually (a concurrency group keyed to skip-if-superseded rather than cancel-in-place would avoid this), but out of scope for this pass.

### Good-to-have

5. **No `shared/metrics` package** — each service that does implement `/metrics` does so independently, the same "solved twice" pattern rate-limiting was. Previously framed as depending on item 1 (no point centralizing instrumentation for a stack nothing scrapes yet) — since item 1 is now cancelled rather than merely pending, this dependency is moot until/unless the user revisits observability; don't treat it as blocked-and-waiting.
6. **No formal API-versioning/deprecation strategy** beyond the fixed `/api/v1/` convention — fine today, but there's no tooling or process for introducing a breaking `/v2` when the platform eventually needs one.
7. **CDN does TLS/IP-preservation only, no asset caching.** Cloudflare sits in front of `*.codevertexafrica.com` for latency (Kenya↔origin RTT) and IP preservation, but no `Cache-Control` headers or CDN-level asset caching were found in any ingress config. Lower urgency — the POS-load-speed work already shipped gzip + client-side cache-first fixes that addressed the original symptom this would have targeted.
10. ~~**Read-replica routing exists for pos-api/inventory-api only.**~~ **LANDED 2026-08-21 for treasury-api.** treasury-api's `arpa`/`reconciliation` modules now route AR/AP aging reports, customer/vendor statement, and the bank-reconciliation unmatched-lines list through a `treasury_ro` pgbouncer alias (`treasury-api 42569fc` + `devops-k8s d41e7688`, pool_size deliberately kept at 4 — same conservative value as `inventory_ro`/`pos_ro`'s post-incident setting, not the briefly-tried 8, given the replica's disk-I/O ceiling documented in `pgbouncer.yaml`'s own comments). Built, deployed, verified healthy (2/2 pods, 0 restarts, no errors in logs). **Still open: the `POSTGRES_READONLY_URL` secret key itself isn't populated yet** — currently a safe no-op falling back to the primary, same bootstrapping pattern pos-api/inventory-api went through initially. auth-api/subscriptions-api remain lower priority — their read patterns are mostly single-row lookups, not heavy scans.

### Actioned this pass — WAF/DDoS (moved out of "explicitly out of scope")

11. **WAF/DDoS protection — was zero, now being closed via Cloudflare's managed ruleset.** No WAF config existed repo-wide beyond the existing nginx rate-limit annotations and Cloudflare's orange-cloud DNS proxying (edge TLS/IP-preservation, not a committed firewall ruleset). Per an explicit 2026-08-21 decision, the platform is adopting **Cloudflare's managed WAF ruleset** (dashboard-level, near-zero engineering cost) as the pragmatic first layer, rolled out in Log-then-Block mode to avoid false-positive-blocking real customer traffic — not a self-hosted ModSecurity/ingress-nginx WAF, which remains a bigger, not-yet-justified investment.

### Explicitly out of scope for this pass — flagged for a future, separate audit

Blue-green/canary rollout policy (ArgoCD's sync policy specifically wasn't audited), chaos engineering, multi-region/DR beyond the existing tenant-scoped backup CronJobs, feature flags as a formal system, SLO/SLI/error-budget practice, cost optimization. These came from the reference best-practices checklist this audit was run against, but weren't part of this pass's targeted scan — don't assume they're fine just because they're not listed as a confirmed gap above. (WAF/DDoS protection was in this list as of the original 2026-08 audit — see item 11 above, now being actioned rather than deferred.)

## How to action this list

Each numbered item above is independent and should be scoped, reviewed, and approved on its own — this list is deliberately a menu, not a bundled project. If you're picking one up, start by re-verifying the gap still exists (this audit is a point-in-time snapshot) before scoping the fix.
