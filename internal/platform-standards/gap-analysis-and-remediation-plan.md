# Best-Practices Gap Analysis & Remediation Plan

> **INTERNAL ONLY — do not publish.** This file lives under `shared-docs/internal/` specifically because it is not built into the public docs site (see `mkdocs.yml`'s `docs_dir`). It's the fleet-wide, centralized record of known infrastructure/architecture gaps — effectively a map of the platform's current weak points — which is exactly the kind of thing that shouldn't be handed to the public alongside the developer-facing guide content. The published [Platform Engineering Standards](../../docs/platform-standards/index.md) pages describe how each piece of infrastructure works and are safe to publish; they deliberately do NOT restate the gap analysis below. Cross-referenced from the project's own memory system — see `d:\Projects\Codevertex\.claude\memory\deferred-and-open-items.md`.

Compiled 2026-08 from a live prod cluster inspection (`ssh mss-prod` / `kubectl`) plus a targeted scan of `shared/` and `devops-k8s/`, checked against a general best-practices reference spanning codebase, deployment, scalability, security, and performance. This page is the single compiled list — the individual [Platform Engineering Standards](../../docs/platform-standards/index.md) pages used to link back here for the specific gaps they called out; that cross-linking was removed when the public pages were rewritten to be gap-free, so this file is now the only place this analysis lives. **Nothing on the "confirmed gaps" list below has been implemented as part of this audit** — this is a gap analysis and proposed task list for sign-off, not a changelog. Prod-infrastructure changes carry real blast radius and should be reviewed and approved individually before work starts.

## Confirmed gaps — prioritized remediation task list (proposed, needs sign-off per item)

### Must-have

1. ~~**No observability stack.** Zero Prometheus/Grafana/Loki/tracing-backend pods anywhere in the cluster... Proposed: deploy kube-prometheus-stack + Loki.~~ **NOT A GAP — corrected 2026-08-06, re-confirmed and fully closed out 2026-08-16.** This framing was stale against a deliberate decision: `devops-k8s` commits `aa18b5ca`/`402faacc` (2026-07-13) decommissioned the self-hosted kube-prometheus-stack on purpose, its own message stating "Replaced by lightweight admin-panel scripts on auth-service reading kubectl top / metrics-server directly." A session that treated this line item at face value nearly re-deployed the full stack in 2026-08-06 (caught before anything went live). Separately, an out-of-band `kubectl apply` of a full `kube-prometheus-stack` release (ArgoCD Application `prometheus`, bypassing this repo's GitOps path entirely) was found actually running live in `infra` on 2026-08-16 during a production incident post-mortem — origin unknown, never landed in this repo or its history. The user explicitly revisited the decision that day and confirmed: tear it down for good. Fully removed 2026-08-16: the ArgoCD Application, all Helm-release-owned workloads/services/ingress/secrets/configmaps/ServiceMonitors (64 resources), the `Prometheus`/`Alertmanager` CRs and their StatefulSets, all 3 PVCs (40Gi), all 10 `monitoring.coreos.com` CRDs, plus long-orphaned leftovers from the *original* pre-decommission release (`monitoring-grafana` secret/configmaps, `grafana-tls`, `prometheus-kube-prometheus-admission` — all 243-257 days old, never cleaned up until now) and this repo's own dead `manifests/monitoring/`, `docs/monitoring.md`, `scripts/monitoring/`. The gap this closed — no push-based alerting — is now handled by `fleet-health-watcher` (a lightweight CronJob, Slack + email), not a re-deployed TSDB stack. **Do not propose re-deploying Prometheus/Grafana/Loki again without the user explicitly revisiting this decision first** — that's now happened twice; a third occurrence should be treated as a strong signal to actually ask the user directly rather than infer it from a stale doc line again.
2. **LANDED 2026-08-07 — controller live, pilot migration complete.** Sealed Secrets controller (bitnami chart v2.19.1, not External Secrets Operator — no external KMS/Vault exists in this stack, so ESO would add an operator layer for no benefit over Sealed Secrets' simpler in-cluster-keypair model) is live in `kube-system`, verified via `kubeseal --fetch-cert`. `apps/sealed-secrets-manifests/app.yaml` scaffolds directory-sync of future per-service `SealedSecret` files so migrating a new service is just "add a file" — no new Application needed per service. Pilot migration (`library-api-secrets`) completed and fully verified: the `SealedSecret` now owns the resulting Secret, all 13 original keys intact, consuming pods undisturbed throughout. Two operational gotchas hit and resolved — the controller won't take over a pre-existing plain Secret, and won't re-reconcile on that Secret's deletion alone (needs a controller pod restart to force a fresh full reconcile) — documented in `.claude/memory/reference_sealed_secrets_migration_gotchas.md` for every future per-service migration. No dashboard/UI for Sealed Secrets — that's by design (the decrypting key never leaves the cluster); a future thin admin-panel wrapper was discussed and deferred, not built. Remaining services still need one-at-a-time migration, ascending blast radius, per the original plan (defer `auth-api`/treasury/payment-gateway secrets to last).
3. **LANDED 2026-08-06.** All three pieces live and verified on prod: PgBouncer `replicas: 1→2` + a `PodDisruptionBudget`; a new, purely-additive Postgres streaming-replication standby (`pg_basebackup`-primed, confirmed via `pg_stat_replication` showing `state=streaming` with single-digit-millisecond lag, write-rejection confirmed, zero primary downtime during setup); a new, purely-additive Redis replica (confirmed via an actual write-on-master/read-from-replica propagation test, not just a link-up check). This is single-node accepted-risk HA — protects against a primary pod crash/OOM/bad-migration, not node/disk failure, since both pods share the same physical disk. No automatic failover for either database; manual-promotion runbook documented in `shared-docs/internal/operations/database-maintenance.md`. The "should this be monitored via Prometheus" question flagged in the prior note was resolved by not needing it — `pg_stat_replication`/Redis `INFO replication` plus the existing lightweight kubectl-based approach were sufficient to verify and will be sufficient to operate this going forward.
4. ~~**Rate-limiting logic duplicated per-service instead of centralized.**~~ **DONE 2026-08-06:** extracted to `github.com/Bengo-Hub/shared-ratelimit` (`Limiter` for treasury-api's sliding-window abuse throttling, `Quota` for notifications-api's daily plan-quota metering); both services migrated. See [Rate Limiting](../../docs/platform-standards/rate-limiting.md) (updated).

### Good-to-have

5. **No `shared/metrics` package** — each service that does implement `/metrics` does so independently, the same "solved twice" pattern rate-limiting was. Previously framed as depending on item 1 (no point centralizing instrumentation for a stack nothing scrapes yet) — since item 1 is now cancelled rather than merely pending, this dependency is moot until/unless the user revisits observability; don't treat it as blocked-and-waiting.
6. **No formal API-versioning/deprecation strategy** beyond the fixed `/api/v1/` convention — fine today, but there's no tooling or process for introducing a breaking `/v2` when the platform eventually needs one.
7. **CDN does TLS/IP-preservation only, no asset caching.** Cloudflare sits in front of `*.codevertexafrica.com` for latency (Kenya↔origin RTT) and IP preservation, but no `Cache-Control` headers or CDN-level asset caching were found in any ingress config. Lower urgency — the POS-load-speed work already shipped gzip + client-side cache-first fixes that addressed the original symptom this would have targeted.

### Explicitly out of scope for this pass — flagged for a future, separate audit

WAF/DDoS protection, blue-green/canary rollout policy (ArgoCD's sync policy specifically wasn't audited), chaos engineering, multi-region/DR beyond the existing tenant-scoped backup CronJobs, feature flags as a formal system, SLO/SLI/error-budget practice, cost optimization. These came from the reference best-practices checklist this audit was run against, but weren't part of this pass's targeted scan — don't assume they're fine just because they're not listed as a confirmed gap above.

## How to action this list

Each numbered item above is independent and should be scoped, reviewed, and approved on its own — this list is deliberately a menu, not a bundled project. If you're picking one up, start by re-verifying the gap still exists (this audit is a point-in-time snapshot) before scoping the fix.
