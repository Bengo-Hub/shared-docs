# Best-Practices Gap Analysis & Remediation Plan

> **INTERNAL ONLY — do not publish.** This file lives under `shared-docs/internal/` specifically because it is not built into the public docs site (see `mkdocs.yml`'s `docs_dir`). It's the fleet-wide, centralized record of known infrastructure/architecture gaps — effectively a map of the platform's current weak points — which is exactly the kind of thing that shouldn't be handed to the public alongside the developer-facing guide content. The published [Platform Engineering Standards](../../docs/platform-standards/index.md) pages describe how each piece of infrastructure works and are safe to publish; they deliberately do NOT restate the gap analysis below. Cross-referenced from the project's own memory system — see `d:\Projects\Codevertex\.claude\memory\deferred-and-open-items.md`.

Compiled 2026-08 from a live prod cluster inspection (`ssh mss-prod` / `kubectl`) plus a targeted scan of `shared/` and `devops-k8s/`, checked against a general best-practices reference spanning codebase, deployment, scalability, security, and performance. This page is the single compiled list — the individual [Platform Engineering Standards](../../docs/platform-standards/index.md) pages used to link back here for the specific gaps they called out; that cross-linking was removed when the public pages were rewritten to be gap-free, so this file is now the only place this analysis lives. **Nothing on the "confirmed gaps" list below has been implemented as part of this audit** — this is a gap analysis and proposed task list for sign-off, not a changelog. Prod-infrastructure changes carry real blast radius and should be reviewed and approved individually before work starts.

2. ~~**Sealed Secrets migration of the 5 critical services.**~~ **FULLY LANDED 2026-08-21 — all 5 migrated and live-verified.** Sealed Secrets controller (bitnami chart v2.19.1, not External Secrets Operator — no external KMS/Vault exists in this stack, so ESO would add an operator layer for no benefit over Sealed Secrets' simpler in-cluster-keypair model) is live in `kube-system`, verified via `kubeseal --fetch-cert`. `apps/sealed-secrets-manifests/app.yaml` scaffolds directory-sync of future per-service `SealedSecret` files so migrating a new service is just "add a file" — no new Application needed per service. Pilot migration (`library-api-secrets`, 2026-08-07) completed and fully verified first; the same recipe then ran for all 5 critical services in ascending blast radius — `pos-api` (`devops-k8s 89c1b544`) → `inventory-api` (`73bce567`) → `subscription-api` (`0543492b`) → `treasury-api` (`48e4cc30`) → `auth-api` (`2d745279`). Every migration hit the same two documented gotchas (controller won't take over a pre-existing plain Secret; won't re-reconcile on deletion alone, needs a controller restart) and was independently live-verified: `SYNCED: True`, `ownerReference` is the `SealedSecret`, exact key-list match against the pre-migration secret (not just a count — a full diff), consuming pods stayed `Running` with 0 new restarts throughout, plus a real SSO smoke test (`sso.codevertexafrica.com`'s JWKS endpoint, `HTTP 200`) after auth-api's migration specifically. Two things deliberately scoped OUT: `subscriptions` namespace's stale, unreferenced plural `subscriptions-api-secrets` (12 keys, orphaned leftover from the historical singular/plural DNS naming bug — the live one is singular `subscription-api-secrets`, 13 keys, confirmed via its `envFromSecret` reference) was left untouched, not migrated; `auth` namespace's JWT signing-key secrets (`auth-token-keys`/`auth-service-token-keys`), `auth-ui-env`, and the TLS secrets were also left as plain Secrets — out of scope for this pass, meaningfully higher blast radius than a DB/Redis credential rotation, a separate future decision. No dashboard/UI for Sealed Secrets — that's by design (the decrypting key never leaves the cluster); a future thin admin-panel wrapper was discussed and deferred, not built.
3. **LANDED 2026-08-06; re-verified 2026-08-21, one sub-gap found and closed same day.** All three pieces live and verified on prod: PgBouncer `replicas: 1→2` + a `PodDisruptionBudget`; a new, purely-additive Postgres streaming-replication standby (`pg_basebackup`-primed, confirmed via `pg_stat_replication` showing `state=streaming` with single-digit-millisecond lag, write-rejection confirmed, zero primary downtime during setup); a new, purely-additive Redis replica (confirmed via an actual write-on-master/read-from-replica propagation test, not just a link-up check). This is single-node accepted-risk HA — protects against a primary pod crash/OOM/bad-migration, not node/disk failure, since both pods share the same physical disk. No automatic failover for either database; manual-promotion runbook documented in `shared-docs/internal/operations/database-maintenance.md`. The "should this be monitored via Prometheus" question flagged in the prior note was resolved by not needing it — `pg_stat_replication`/Redis `INFO replication` plus the existing lightweight kubectl-based approach were sufficient to verify and will be sufficient to operate this going forward. **Found and fixed same day (2026-08-21): the `postgresql` StatefulSet itself had no PodDisruptionBudget** (pgbouncer and redis-master each had one; the primary database didn't) — added (`devops-k8s a3d7f833`, applied via `kubectl` directly after `provision.yml` got raced/cancelled — see the release-bot-race note below), verified live (`kubectl get pdb postgresql -n infra` shows `minAvailable=1`).

8. ~~**New 2026-08-21 — no NetworkPolicy or Pod Security Standards anywhere in the cluster.**~~ **NetworkPolicy CLOSED for the 6 highest-risk services same day (2026-08-21).** `kubectl get networkpolicy -A` had returned only ArgoCD/Calico-apiserver/ollama-shared entries — zero pod-to-pod isolation existed for `pos`/`inventory`/`treasury`/`auth`/`subscriptions` (or any other app namespace); any pod that could reach the cluster network could reach any other service's pods, PgBouncer, and Redis directly. Fixed via ingress-only `NetworkPolicy` manifests (new `manifests/network-policies/` directory-sync Application, mirroring `sealed-secrets-manifests`' pattern) — deliberately Ingress-only, NOT using the shared `charts/app` chart's own bundled `networkpolicy.yaml` template, whose default Egress allow-list (only `infra` namespace + external :443) would have silently broken cross-namespace S2S calls (confirmed against library-api's real NATS/treasury/notifications/subscriptions dependencies — a real footgun in that shared template worth fixing before anyone else flips `networkPolicy.enabled` on it). Piloted on `library-api` (`devops-k8s d79a20d9`) then extended to all 5 critical services (`devops-k8s f62bc387`/`86139a7c`/`a1a4b397`/`aa126c77`/`3c59c77e`). **Each namespace's consumer list was derived two ways, and the second check found a real miss the first alone would have shipped as a live-outage risk**: (1) grepping every `apps/*/values.yaml` for explicit internal-DNS overrides, and (2) grepping every service's Go `config.go` for a compiled-in default already pointing at internal DNS with *no* values.yaml override — treasury-api's own `SUBSCRIPTION_BASE_URL` defaults straight to subscription-api's internal DNS this way, invisible to a values.yaml-only grep. The same sweep also surfaced a separate, pre-existing, unrelated bug (documented, not fixed, not allow-listed): logistics-api's treasury client defaults to port 4005, but treasury-api's Service only exposes 4000 — already broken before this policy existed. Every one of the 6 policies was live-verified, not just deployed: 0 new pod restarts, the service's public hostname still responds, every real consumer namespace confirmed reachable via a live in-cluster request, and at least one non-allow-listed namespace confirmed genuinely blocked (`HTTP 000`) per service. **Pod Security Standards: observe-only LANDED same day.** `pod-security.kubernetes.io/warn: baseline` + `audit: baseline` added to all 5 namespaces (`devops-k8s c266cdbc`, new `manifests/pod-security-standards/` Namespace manifests, same directory-sync Application pattern as `network-policies`/`sealed-secrets-manifests`) — deliberately no `enforce` label (Kubernetes defaults `enforce` to `privileged`/unrestricted when absent, so this cannot block any pod admission). Checked every Deployment's `securityContext` first (pos-api/inventory-api already set non-root `runAsUser`/`runAsGroup`/`fsGroup`; auth-api sets `runAsNonRoot: true`; no privileged containers or host namespaces found anywhere in the fleet), then live-verified after applying: `kubectl get events --field-selector reason=PodSecurity` returned **zero** warnings across all 5 namespaces on real, freshly-recreated pods (several were mid-deploy from unrelated image-tag bumps during this session) — confirms every one of the 5 already cleanly complies with the baseline profile, not just that labels were added. `shared-infra`'s namespace already runs `enforce: baseline` in prod as a working precedent for flipping these 5 to enforce too — a real, low-risk next step now that the audit signal is confirmed clean, but a separate decision, not bundled into this pass.
9. **New 2026-08-21 — VPA live-in-cluster but absent from GitOps; KEDA installed but unused. GitOps-capture LANDED same day for VPA.** `kubectl get vpa -A` showed a VPA object (mode `Off`) for all 5 critical services, but none of their `values.yaml` defined a `verticalPodAutoscaling` block — these were applied out-of-band and were pure cluster drift, not GitOps-managed. Fixed: added the matching block (mode `Off`, matching live state exactly — a mode change is a separate, later decision) to all 5 `values.yaml` (`devops-k8s a3d7f833`), verified zero behavior change (same spec, same object age, no recreation). Separately, the KEDA operator is running (3 pods, `infra`) but zero `ScaledObject`s exist anywhere — the earlier "HPA + VPA + KEDA, fleet-wide" framing in this doc's own "confirmed working well" table overstated actual KEDA usage; KEDA is an installed, unused capability, not an active autoscaling mechanism, and is left as-is (a capability to reach for on a future queue-depth-sensitive workload, not something that needs a `ScaledObject` today just to prove it works).

**Recurring operational footgun found this pass (not itself a gap item, but worth recording here since it affected several of the fixes above):** `devops-k8s`'s `provision.yml` — the workflow that applies new/changed ArgoCD `Application` CRs (as opposed to plain `values.yaml` content, which ArgoCD picks up on its own git-polling cycle) — gets raced and cancelled by the very next push almost every time (matches [[reference_devops_k8s_release_bot_ci_race]]). Every `app.yaml`-level change in this pass (the `postgresql` Application's `directory.include` edit, the new `network-policies` Application) needed a direct `kubectl apply -f apps/<x>/app.yaml` fallback after confirming via `gh run list` that the workflow run was cancelled. Worth fixing at the workflow level eventually (a concurrency group keyed to skip-if-superseded rather than cancel-in-place would avoid this), but out of scope for this pass.

### Good-to-have

5. **No `shared/metrics` package** — each service that does implement `/metrics` does so independently, the same "solved twice" pattern rate-limiting was. Previously framed as depending on item 1 (no point centralizing instrumentation for a stack nothing scrapes yet) — since item 1 is now cancelled rather than merely pending, this dependency is moot until/unless the user revisits observability; don't treat it as blocked-and-waiting.
6. **No formal API-versioning/deprecation strategy** beyond the fixed `/api/v1/` convention — fine today, but there's no tooling or process for introducing a breaking `/v2` when the platform eventually needs one.
7. **CDN does TLS/IP-preservation only, no asset caching.** Cloudflare sits in front of `*.codevertexafrica.com` for latency (Kenya↔origin RTT) and IP preservation, but no `Cache-Control` headers or CDN-level asset caching were found in any ingress config. Lower urgency — the POS-load-speed work already shipped gzip + client-side cache-first fixes that addressed the original symptom this would have targeted.
12. **New 2026-08-21 — dashboard/report aggregate endpoints are consistently uncached fleet-wide, unlike catalog/reference-data lookups.** `shared/cache`'s `Aside[T]` covers reference data well (tenant branding, subscription/feature gates, VAT-rate memoization — see the "confirmed working well" table above), but every heavy *aggregation* endpoint checked recomputes from Postgres on every single request, with no caching layer at all: pos-api's `ReportsHandler.GetSummary`/`DailyBreakdown` (`internal/http/handlers/reports.go` — the dashboard KPI cards, queries `POSOrder.WithLines()` across two full periods plus a gross-profit per-SKU cost resolution, on every page load), inventory-api's ingredient-utilization report (`internal/modules/reports/ingredient_utilization*.go`), and treasury-api's `finance/aggregates.go` (NetProfit/equity — the platform-owner P&L dashboard). Deliberately **not implemented in this pass** rather than rushed: pos-api's `GetSummary` specifically has *documented prior scoping-bug history* on this exact handler (`pos-dashboard-catalog-outlet-scoping-2026-08-07.md` — "Top Selling Items/Daily Breakdown had NONE [outlet-scoping] — tenant-wide leak") and its result set varies per-caller along multiple axes (`tenant`, `outlet` filter, and a per-cashier `ownOrdersScope` RBAC predicate that scopes a plain cashier to only their own sales) — a cache key that drops any one of those dimensions would silently leak one user's/outlet's numbers to another, exactly the bug class that handler has hit before. Per [[feedback_thorough_testing_before_prod_live_clients]], a change like this needs a real multi-role E2E test (cashier vs. manager, two different outlets) before being called done, not just a unit-level correctness check — better scoped as its own follow-up than squeezed into this pass. **Design sketch for whoever picks this up:** `TTLOperational` (30s) tier per the existing three-tier convention; cache key must include `tenant_id` + resolved `outlet_id` filter + (when `ownOrdersScope` applies) the scoping user's ID + the exact `from`/`to` window — do not cache the RBAC-scoped and unscoped variants under the same key. inventory-api's and treasury-api's report endpoints are lower-risk (no per-user RBAC-scoping variance found) and are more straightforward first candidates if this is picked up.
10. ~~**Read-replica routing exists for pos-api/inventory-api only.**~~ **LANDED 2026-08-21 for treasury-api.** treasury-api's `arpa`/`reconciliation` modules now route AR/AP aging reports, customer/vendor statement, and the bank-reconciliation unmatched-lines list through a `treasury_ro` pgbouncer alias (`treasury-api 42569fc` + `devops-k8s d41e7688`, pool_size deliberately kept at 4 — same conservative value as `inventory_ro`/`pos_ro`'s post-incident setting, not the briefly-tried 8, given the replica's disk-I/O ceiling documented in `pgbouncer.yaml`'s own comments). Built, deployed, verified healthy (2/2 pods, 0 restarts, no errors in logs). **Still open: the `POSTGRES_READONLY_URL` secret key itself isn't populated yet** — currently a safe no-op falling back to the primary, same bootstrapping pattern pos-api/inventory-api went through initially. auth-api/subscriptions-api remain lower priority — their read patterns are mostly single-row lookups, not heavy scans.

### Actioned this pass — WAF/DDoS (moved out of "explicitly out of scope")

11. ~~**WAF/DDoS protection — was zero.**~~ **Log mode LANDED 2026-08-21.** No WAF config existed repo-wide beyond the existing nginx rate-limit annotations and Cloudflare's orange-cloud DNS proxying (edge TLS/IP-preservation, not a committed firewall ruleset). Closed via **Cloudflare's managed WAF ruleset**, deployed through a new scripted, idempotent path (`devops-k8s/scripts/cloudflare/manage-waf.py` + `.github/workflows/cloudflare-manage-waf.yml`, a dedicated `CF_WAF_API_TOKEN` GitHub secret) rather than a one-off manual dashboard click — not a self-hosted ModSecurity/ingress-nginx WAF, which remains a bigger, not-yet-justified investment. **Real finding along the way: `codevertexafrica.com` is on Cloudflare's Free plan** — the paid-tier "Cloudflare Managed Ruleset"/"OWASP Core Ruleset" originally planned don't exist on this account; what's actually deployed is the **Cloudflare Managed Free Ruleset**, discovered live via the Rulesets API and confirmed via `gh secret list` cross-checking `CF_API_TOKEN`'s narrow existing DNS-only scope (which is why a separate, dedicated `CF_WAF_API_TOKEN` was created rather than reusing it). 13. ~~**`provision.yml` (the cluster-bootstrap workflow) triggered on every single push to devops-k8s, with no path filter.**~~ **FIXED 2026-08-21.** Requested audit: "why does provisioning.yaml keep failing." It doesn't, really — `gh run list` on the last 100 runs showed 63 cancelled, 35 succeeded, **zero genuine failures**. Root cause: the workflow's own `push` trigger had no `paths:` filter, so every commit to the repo ran the full ~6-7min cluster-bootstrap (VPS liveness check via Contabo API, namespace/secret provisioning, cert-manager, ingress, databases, ArgoCD itself, and — critically — the `for app_file in apps/*/app.yaml; do kubectl apply -f "$app_file"; done` loop that's the *only* mechanism applying new/changed ArgoCD Application CRs, since ArgoCD's own reconciliation doesn't self-manage Application resources here). Every one of the release-bot's routine per-service image-tag-bump commits (which ArgoCD's own git-polling already handles with zero need for this workflow) triggered a run too, and the workflow's own `cancel-in-progress: false` concurrency policy collapses the pending-run queue to 1, cancelling older runs — so any provisioning-relevant push landing near a routine deploy had a real chance of being silently cancelled before ever reaching the Application-CR-apply step, with no automatic retry (this session hit it repeatedly — `network-policies` and `pod-security-standards`, both brand-new Applications, needed a manual `kubectl apply -f apps/<x>/app.yaml` fallback after their provision.yml runs got cancelled). Fixed: scoped the `push` trigger to `manifests/**`, `scripts/**`, `apps/**/app.yaml`, `apps/root-app.yaml`, the workflow file itself, and `.github/actions/**` — every path this workflow's own steps actually read (verified via grep, including inside `install-databases.sh`). Routine service deploys no longer touch this workflow at all; `workflow_dispatch` (e.g. after a VPS migration) is unaffected. `devops-k8s 5a0beea0`.
14. **New 2026-08-21, found while auditing VPS-migration readiness — the Sealed Secrets controller's master private key was never backed up anywhere. FIXED same day.** The controller (installed via `apps/sealed-secrets/app.yaml`, already automated through the generic Application-CR loop above) generates its own keypair in-cluster on first start if none exists — the live one was generated 2026-08-06 and lived *only* there, with no backup procedure anywhere in the repo. Every `*.sealedsecret.yaml` file under `manifests/sealed-secrets/` (6 services as of this session) is encrypted specifically against that key; losing the VPS without a backup would have made all of them permanently undecryptable, requiring manual re-entry of every credential from scratch on a fresh cluster — the single biggest gap found against "minimal manual setup on migration." Fixed: the live key was backed up as a new `SEALED_SECRETS_MASTER_KEY` GitHub Actions secret (piped directly from `kubectl get secret ... -o yaml` to `gh secret set`, never displayed), and a new provision.yml step restores it from that secret *before* ArgoCD/the sealed-secrets Helm release exist on a fresh cluster — so a migrated cluster's controller starts with the *same* keypair instead of generating an incompatible new one. The restore step never overwrites an already-present live key (checked via label selector first) — a stale backup can never clobber a real, possibly-since-rotated, in-cluster key. `devops-k8s 7d49f444`. **Rotate/backup-refresh trigger also LANDED same day**, via auth-api's platform-admin "Infrastructure Monitor" panel — deliberately never touches or displays the key material through the UI or auth-api itself: a new `SealedSecretsHandler` (`GET/POST /api/v1/admin/infra/sealed-secrets/{status,rotate}`, platform-owner gated, `auth-api 7de9f8d`) dispatches a new `devops-k8s` `sealed-secrets-key-rotate.yml` (`workflow_dispatch`, `781338b8`) via the GitHub Actions API using a new, narrowly-scoped `DEVOPS_REPO_TOKEN` (fine-grained PAT, *Actions: write only* — deliberately NOT `Secrets: write`, since the workflow itself reuses the existing `PROPAGATE_PAT`/`GH_PAT` for the actual `gh secret set` call). "Rotate" restarts the controller (triggers its own `--key-renew-period` logic if due) then refreshes the backup either way; old keys are never deleted, so rotation history never breaks existing sealed secrets. New `SealedSecretsCard` in auth-ui (`799b585`) shows backup status/last-refresh time and the two trigger buttons. All three pieces build clean (`go build`/`go vet`/`pnpm build`). **Still open:** the `DEVOPS_REPO_TOKEN` itself needs the user to generate the PAT and populate it into `auth-api-secrets` (now a SealedSecret, so this needs the same seal-and-merge dance as any other key addition) before the feature is actually usable — currently deploys safely and returns a clear "not configured" status until then.

## How to action this list

Each numbered item above is independent and should be scoped, reviewed, and approved on its own — this list is deliberately a menu, not a bundled project. If you're picking one up, start by re-verifying the gap still exists (this audit is a point-in-time snapshot) before scoping the fix.
